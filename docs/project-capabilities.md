## 本轮消除的实际耦合

- 共享契约和数据库原先将活动限制为 `lab`。现在使用统一 slug 标识，新增 `003_campaign_catalog` 迁移；没有改写已应用的 `001/002`。
- 活动查询改为 `/api/campaigns/:campaignId`；参与及事件写入先经过 Catalog 校验。移除硬编码没有放宽为接受任意活动。
- SDK 必须显式配置 campaignId；重发使用原回执中的活动 ID。只有验收页面入口集中保留 `lab` 常量。
- 同一会话、同一个 round 在不同活动中有独立回执；本轮事件统计同时过滤 owner、campaign 与 round。会话累计另行标为跨活动累计。
- Catalog 完整检查版本、标题和素材字段，配置错误在启动时失败，而不是延迟到浏览器。

## 添加后续活动

在受版本控制的配置中提供符合 CampaignSchema 的活动，通过 `buildApp({ store, config, campaigns })` 注册；新增素材须有版本化文件名和清单。正式页面使用通用 `api.campaign(id)` 和带活动 ID 的 TelemetryClient，再实现自身 UI/场景。

现有交互类型明确是 timing/swipe。新增玩法需要版本化契约演进与场景实现，不承诺零代码；不需要因此重写活动目录、会话、事件接收、数据库幂等或同源交付层。当前关键音频/视频会显式报未支持，不能把类型预留误称为完整多媒体管线。

`/api/lab/verification/:id` 是受会话保护的开发核验入口，不是全库调试接口。生产观测目前没有完整 APM/告警平台；Pino、request ID 和手动读回不应被称为生产全链路监控。
